# 应用背景信息

应用知识维护在 `src/model/app-info.ts` 的 `appInfoMap`，以实际 Bundle ID 为键。每项包含显示名称、分类、用途与常见功能；只记录通用背景，不记录用户会话或账户信息。

`resolveAppInfo` 返回独立的请求快照：原始 Bundle ID、观测名称、来源、知识表版本和定义。未知 ID 不按名字猜用途，尤其 `com.github.Electron` 是多个开发应用共用的通用 ID，不能当作某个具体产品。应用名称和窗口身份校验是两个不同问题；Dock 被误判为点击目标时，知识表无法修复错误截图。

用途和功能是解释画面的背景，不是当前行为的证据。浏览器不说明当前网站；编辑器不代表用户正在写代码；微信的功能列表也不代表当前使用了其中某个功能。模型必须以当前操作、截图、AX 和 OCR 确认具体行为。

修改知识表后重新构建启动。本功能不扫描应用的私有数据、不联网自动扩充知识，也不创建记忆或触发业务操作。

数据链路：动作的 `app.bundle_id/name` → `resolveAppInfo` → 屏幕理解模板 `app_info` → 实际 User Prompt、缓存哈希和 `debug.promptInput` → 理解结果的轻量 `app_info` 快照 → 主 Agent 批次消息。主 Agent 按应用快照去重，并通过 `action_ids` 对应具体动作，不发送整份知识表。

知识表更新会改变未来理解输入与缓存键，不修改旧请求。主 Agent 使用理解时保存的快照，不在投递时重新查表；旧结果没有 `app_info` 时明确为 null。设置中的系统 Prompt 即使有自定义覆盖，User 模板仍保留硬件事件、视觉证据与应用背景的职责说明。

硬件事件保持原样：它约束操作类型，VLM 不得凭画面将右键改成左键、将空格改成点击发送。App 背景不替代事件、点击坐标和目标窗口身份。此次不修改事件过滤、截图、坐标输入或 Dock 归属逻辑。
