# 列表刷新与界面内存优化

日期：2026-09-08。

## 实际问题

- `ActionQueue.list()` 每次刷新对所有 `result` 做三次 `json_extract`。本机 254 条记录的完整结果约 197 MB，单次只读查询实测为 244–251 ms。同步查询占用 Electron 主进程，使其他 IPC、窗口交互与事件处理排队。
- `understanding.completed` 把完整 `manifest` 和 `debug` 放进常驻事件数组，`snapshot` 再反复把它们发送到 renderer。原始 AX 和 Prompt 随每次状态刷新重复复制，不是只有打开详情才加载。
- 实测旧 renderer 在启动约 139 秒时发生 V8 OOM，崩溃前堆容量约 3.4 GB；不能把进程退出后的低 CPU 当作优化效果。
- 历史列表每秒串行重读全部 `meta.json`，同一次理解还重复读取完整快照。

## 修改边界

- 队列打开时投影一次已有摘要，之后在 enqueue、理解完成、状态变化和 retry 时逐条更新轻量缓存。`list()` 不执行 SQL，也不缓存原始结果。完整结果仍通过 `result(actionId)` 读取。
- 给待处理队列添加覆盖索引，降低调度状态扫描成本。未删除、重写或压缩已有证据。
- 完成通知只保留 action ID、模型、摘要、用量、耗时和输入哈希；完整 Prompt、AX、图像和响应继续保存在 SQLite / trace 文件中，侧栏按需读取。
- 历史列表仍扫描目录以发现新增和删除，但已知记录的元数据使用缓存；本应用 save/update/remove 同步更新缓存。并发列表请求共享扫描。其他进程直接改写同 ID 的 `meta.json` 不受支持，重启后重新读取。
- 同一次理解只读一次完整 AX 快照；UI 刷新合并窗口为 250 ms，仅影响显示刷新，不延迟原生事件与截图请求。
- renderer 崩溃后不再继续向已销毁的 frame 发送通知，避免诊断日志风暴。
- AI 理解并发仍为用户原有设置（默认 10），截图质量、事件过滤和 Agent 路由策略未改变。

## 验证

- 62 项测试通过，包含旧库摘要恢复、状态/重试一致性、完整证据保留、元数据更新和增删、完成事件不携带完整输入。
- 性能回归测试使用约 40 MB 的合成旧结果；初始化后把 SQLite `prepare` 改成抛错，连续调用 100 次 `list()` 仍通过，证明热路径没有重读数据库。
- 在真实数据目录重启新版，使用 `bun scripts/profile-desktop.ts` 从本机调试端口读取耗时/体积/数量，不打印用户记录内容或凭证。
- 新版 306–309 条队列记录：完整 `snapshot` IPC 为 4.4–6.6 ms、载荷约 0.73 MB；477–481 条历史记录的列表读取为 4.4–6.0 ms。
- 约 2 分 39 秒时，开启观察的进程采样为主进程 CPU 5.9%、renderer CPU 3.2%；renderer RSS 约 219 MiB。CPU 是现场采样，和优化前不构成严格同负载实验；RSS 和旧崩溃日志里的 V8 堆容量也不是同一指标。
- 用户已在新版中切换记录和查看图片，界面持续存活。尚未完成小时级持续采集压测，不宣称所有性能问题已消失。

## 复测方法

使用项目正常构建后的 Electron 应用；开发验收启动时添加仅本机的 `--remote-debugging-address=127.0.0.1 --remote-debugging-port=9337`。执行 `bun scripts/profile-desktop.ts 9337` 读取两类 IPC 的 5 次采样。脚本只读，不启动采集、不触发模型，也不输出正文。

需要比较开关观察、理解并发或记录量时，分别记录条件和采样时间；不要将清空历史、停止采集或 renderer 崩溃后的低负载当作修复证据。
